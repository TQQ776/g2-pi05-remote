# G2 π0.5 远程推理控制

本地采集，GPU 服务器远程推理，动作回到本地控制真机。

```
┌──────── 开发机 / 机器人（hybrid deploy, py3.10）────────┐     ┌──── 服务器（4090, py3.11）────┐
│                                                         │     │                                │
│  ──── DDS ────►  Camera ──JPEG──┐                       │     │                                │
│  机器人 10.42.1.101              │                       │     │                                │
│                  Robot  ──24维──┴─► client.py ──TCP─────┼────►│ server.py                      │
│                                       │     8765        │     │   ├─ decode JPEG               │
│                                       │                 │     │   ├─ G2Inputs (state 重排)      │
│                                       │                 │     │   ├─ π0.5 + LoRA 推理           │
│                                       ▼                 │     │   └─ (50,16) action            │
│                                  move_arm_joint_servo ◄─┼─────┤                                │
│                                  move_end_effector_joint│     └────────────────────────────────┘
└─────────────────────────────────────────────────────────┘
```

**客户端跑在哪**：两种都行。

- **混合部署（推荐，也是实测用的）**：GDK 提供 x86_64 构建，直接跑在开发机上，
  通过 DDS 和 `10.42.1.101` 的机器人通信。不用往机器人上拷代码。
  见 `gdk/installer/server_installer.tar.gz` → 解包后 `source <app>/env.sh`，
  必须用 `python3.10`（cp310 ABI）。网口配成 `10.42.1.x/24`，ping 通即可。
- **机器人本体**：仓库里的 `gdk/lib/` 是 aarch64 版，`./run_client.sh` 直接启动。

## 文件

| 文件 | 作用 |

## 快速开始

**1. 服务器先起服务**

```bash
ssh root@<服务器>
cd /root/autodl-tmp/openpi
./server/run_server.sh
```

**1.5 单独读相机（不跑推理）**

```bash
source /mnt/models/gdk_x86/app/env.sh
cd examples/g2_pi05_remote
python3.10 snap.py --out /tmp/camsnap --rounds 20   # 存图 + 测帧率
python3.10 snap.py --no-save --rounds 30            # 只测帧率
```

正常应看到 `~29 Hz`、`enc=Encoding.JPEG`、头部 ~54 KB、腕部 ~285 KB。

**2. 开发机上先验证链路（不需要机器人）**

```bash
python send_fake.py --host <服务器IP> --port 8765 --rounds 5            # 拟真画面
python send_fake.py --host <服务器IP> --port 8765 --pattern noise       # 上行最坏情况
```

正常输出（拟真画面）：

```
第 1 次          往返   467.0 ms  解码  42.2 + 推理 126.8 ms  上行  625.7 KB
第 2 次          往返   314.8 ms  解码  42.1 + 推理 116.6 ms  上行  625.9 KB
```

**3. 机器人上只读验证**

```bash
./run_client.sh --host <服务器IP> --port 8765
```

不加 `--run` 时**不会发任何运动指令**，只打印每轮收到的动作。先确认：

- `帧龄=` 大部分是 0（偶尔几十毫秒可以，几百毫秒以上说明相机在断流）
- `块间停顿=` 接近 0，`网络=` 300–400 ms
- 夹爪数值的符号和量级对不对
- 左臂前三个关节的预测值和当前实际姿态是否接近（差值应该是几十毫弧度量级）

**4. 确认无误后再动**

```bash
./run_client.sh --host <服务器IP> --port 8765 --run --replan-every 18
```

## 姿态保存与还原

开始调机器人之前先把当前姿态存下来，之后任何时候都能回到这个位姿：

```bash
./run_pose_save.sh --name initial --note "部署前初始姿态"   # 只读，不发指令
./run_pose_restore.sh                                     # 空跑，打印每个关节 当前→目标
./run_pose_restore.sh --run                               # 真正还原
./run_pose_restore.sh --run --side right                  # 只还原右臂
```

`pose_save.py` 存的是完整 24 维 state 加上每个关节的 `position` /
`motor_position` / `velocity` / `error_code`、末端执行器的 `type` 和 `names`、
电源与运控状态。还原只用其中的 14 个臂关节；**躯干和头部不动**（那几个电机
现在未上电，而且需要 `move_waist_joint` / `move_head_joint`，不在本脚本范围）。

`pose_restore.py` 的几条约束：

- 余弦缓动，起止速度为零，不会在开始和到位时给电机阶跃；
- 时长不给时按峰值 0.30 rad/s 自动算（训练数据左臂最大速度 0.38 rad/s）；
- 单 tick 变化超过 0.02 rad 直接拒绝执行，不做截断；
- 默认空跑，`--run` 才下发；到位后回读并打印每个关节的到位误差。

## 数据契约

**state（24 维）** —— 顺序和训练数据 `meta/info.json` 严格一致：

```
 0..4   idx01..idx05_body_joint1..5
 5..7   idx11..idx13_head_joint1..3
 8..14  idx21..idx27_arm_l_joint1..7
15..21  idx61..idx67_arm_r_joint1..7
22      gripper_left
23      gripper_right
```

**action（50×16）**：

```
 0..6   左臂 7 关节（绝对关节角，rad）
 7..13  右臂 7 关节（绝对关节角，rad）
14      左夹爪
15      右夹爪
```

客户端只取前 14 维做 `move_arm_joint_servo`，夹爪单独处理。

注意 **24 维 state 的前 14 维不是手臂**，是躯干 + 头部。手臂在 `state[8:22]`。
拿 `state[:14]` 当速度校验的锚点，会算出 86 rad/s 这种离谱数字。

## 三个容易踩的时序问题

**1. 动作块要按往返延迟对齐**

动作块是「从观测那一刻起，每 `period` 一步」的计划。观测发出到结果回来过了 rtt，
所以真正能用的第一个元素是第 `round(rtt / period)` 个，**前面几步已经过期**。
客户端会自动丢掉这些步（日志里的 `对齐跳过=`），按剩余步数执行。

**2. 速度阈值必须分两档**

π0.5 每轮重新采样，同一个观测连跑两次结果就不一样。实测（15 次采样）：

| 指标 | 块内相邻步 | 跨块接缝（第 0 步） |
|---|---|---|
| 中位 | 0.17 rad/s | 1.65 rad/s |
| 最大 | 0.38 rad/s | 3.57 rad/s |

块内是真实轨迹速度，接缝是采样噪声。用同一个阈值会二选一：要么把正常轨迹误杀，
要么放过真正的异常跳变。所以 `--max-speed`（块内，默认 1.0，约 2.6 倍余量）和
`--max-jump`（接缝，默认 8.0，约 2.2 倍余量）分开。

**光有阈值不够，下发侧必须限速。** 这两个阈值都是按 33 ms 的计划步长算的，
而伺服是 100 Hz：新块的第 0 步是在**一个 10 ms tick 内**从上一块末尾跳过去的。
0.267 rad 的计划步长，落到伺服上就是 **27 rad/s 的瞬时阶跃**，电机跟不动，
运控会报 `target joint error over threshold`（`error_code=8`）并锁停。
实测就是这样：一次 0.27 rad 的接缝，`--max-jump 12` 放行之后直接触发锁停。

所以 `--max-target-rate`（默认 2.0 rad/s）给**指令目标本身**限速，跨块连续累进。
0.27 rad 的跃变摊到 14 个 tick（140 ms）里吸收，剩下的 460 ms 正常跟踪。
两个阈值管的是「策略输出是否可信」，限速率管的是「机械臂能不能跟得上」，
调大 `--max-jump` 不再有锁停风险。

锁停后运控 `error_code` 会自己恢复，但要确认关节侧没留下错误码：
`joint_error_code` 非 0 时用 `clear_hal_error()`，运控层的用
`clear_motion_control_error()`，两者不是同一层。

**3. 相机是 28.8 Hz，但**别紧轮询它****

三路轮流取图跑 10 s 实测：**28.8 Hz**，设备时间戳中位间隔 33.3 ms
（271/287 落在 33.3 ms 网格上），和训练数据 30 fps 一致。

**但调用频率会改变测到的帧率**，这点很容易得出错误结论：

| 取图方式 | 实测帧率 |
|---|---|
| 2 ms 紧轮询 | 2.4 Hz |
| 5 ms 超时 + 2 ms 轮询 | 1.5–2.6 Hz |
| 三路轮流 + 50 ms 超时（正常） | **28.8 Hz** |
| 每 500 ms 取一次 | 每次都拿到新帧，耗时 <0.1 ms |

高频调用会饿死 GDK 内部的接收线程，表现出来的就是「相机只有几赫兹」。
所以 `_wait_fresh` 的重试间隔固定 20 ms（大于一帧周期），绝不紧轮询。

`--fresh-timeout` 是**三路合计**预算（默认 50 ms）：相机串行等三次，
每路各等 150 ms 会让主线程整整停 450 ms，日志里就是采图尖峰。
`--max-frame-age`（默认 1 s）兜底：画面真的停滞就抛异常退出，不盲跑。

## 分块推理的接缝：时序集成

π0.5 每一轮都把整块重新采样。同一个观测连推两次，两块在**同一时刻**的预测中位差
0.084 rad——这是流匹配采样的固有随机性。如果照「执行 18 步 → 丢掉剩下的 → 接上
新块第 0 步」的朴素做法，每块交界处就会出现一次跳变。实测（12 块）：

| | 中位 | 最大 |
|---|---|---|
| 块内相邻步速度 | 0.211 rad/s | 0.527 |
| **接缝速度** | **2.857 rad/s** | 6.383 |

接缝是块内的 13.5 倍，表现就是「一抽一抽」——机械臂每 0.6 秒窜一下。

**做法**：不裁剪重叠步，每个时刻把所有覆盖它的预测按 `exp(-m·age)` 加权平均
（ACT 的 temporal ensembling）。两处细节：

- **视野末端要衰减**。`--replan-every 18` 时最新块的 k=18..35 已经覆盖整块，
  更老的块只能提供 k=36..49——50 步视野的尾巴，π0.5 在那里已经退化，同一时刻
  能差 0.3 rad。它掉出缓冲的瞬间均值会突变（实测块内 4.7 rad/s）。
  `--ensemble-taper`（默认 12）让权重在末尾 12 步线性归零，突变消失。
- **两块平均最多减半**。要再往下必须让更多块重叠，也就是缩短 `--replan-every`。

实测对比（只读，同一台机器）：

| 配置 | 块内中位 | 接缝中位 | 接缝最大 | 比值 |
|---|---|---|---|---|
| replan=18，关闭集成 | 0.302 | 3.476 | 4.560 | 11.5× |
| replan=18，开启集成 | 0.572 | 1.815 | 3.720 | 3.2× |
| **replan=14，开启集成** | **0.109** | **0.613** | **0.723** | 5.6× |
| replan=12，开启集成 | 0.095 | 0.496 | 0.683 | 5.2× |

代价是滞后：预测比实际时刻晚一个块，`replan=14` 时约 470 ms。这比原来的
300–400 ms 网络延迟没有实质增加。

`replan=12/14` 的执行预算（400/466 ms）和实测网络 370–470 ms 是临界值，
日志里会间歇出现 `[警告] ... 本轮停顿`。那是公网往返造成的，不是集成的
副作用；**局域网直连可以把往返压到 50 ms 以内，停顿会彻底消失**。
网络确实不够时用 16。

## 关于 `往返` 这个数

`rtt` 是从发包到「读 socket 那一刻」，而读 socket 发生在执行完当前动作块之后。
所以只要网络比动作块快，这个数就恒等于动作块长度（`--replan-every` × 33 ms），
看起来像 500 ms 的平台，其实是测量口径。客户端现在用一个非阻塞探测记录
**首字节真正到达的时刻**，日志里叫 `网络=`。实测 300–400 ms。

## ⚠️ 夹爪：读回正确，下发量纲未验证

- **反馈侧已实测一致**：真机 `get_end_state().end_states[i].position` 读数在
  0.0000 ~ 0.0250，和训练数据夹爪量纲（`norm_stats.json`）对得上。
- **末端执行器身份已确认**：`type=1`，`names=['idx31_gripper_l_inner_joint1']` /
  `['idx71_gripper_r_inner_joint1']`——是夹爪内关节，**不是 omnipicker**。
  所以 `g2_deploy/` 里那套 `[-0.785, 0]` 的 omnipicker 标定不能套到这台机器上。
- **下发侧未验证**：`move_end_effector_joint` 的输入单位还没有标定过。

所以默认 `--gripper-mode hold`（完全不动夹爪）。第一次跑请：

1. 只读模式打印几轮，看模型预测的夹爪值落在什么范围；
2. 用 `g2_deploy/g2_gripper_calibrate.py` 标定张开/闭合对应的 GDK 弧度；
3. 用 `--gripper-mode map --gripper-endpoints L_OPEN L_CLOSE R_OPEN R_CLOSE` 跑；
4. 确认方向正确之后，才考虑 `--gripper-mode raw`。

另外训练集里**右夹爪几乎不动**（全程 0.0250），所以右夹爪的预测基本无意义，
建议保持 `hold` 或固定在下发标定值。

## 时序预算

客户端不是「发出去 → 等结果 → 再动」，而是**先发下一帧、再执行当前块、最后收结果**：
只要一次往返能塞进一个动作块的执行时间里，机械臂就不会因为等网络而停顿。

实测（AutoDL 公网 + SSH 隧道，单帧上行 626 KB 的拟真画面）：

| 环节 | 耗时 |
|---|---|
| 服务端解码三路 JPEG | 42 ms |
| π0.5 推理 | 113 – 117 ms |
| 上行传输 626 KB | ~150 ms |
| **首字节到达（`网络=`）** | **300 – 400 ms** |

30 fps 下每步 33 ms，所以一个往返约等于 9–12 步。据此：

| `--replan-every` | 执行时长 | 覆盖 400 ms 往返 | 说明 |
|---|---|---|---|
| 50（整块） | 1.67 s | 富余 4 倍 | 开环最久，跟手性最差，但最稳 |
| 18–20 | 600–667 ms | 有富余 | **公网推荐**（实测 15 会偶尔停 50 ms） |
| 15 | 500 ms | 临界 | 采图一慢就停顿 |
| 10 | 333 ms | 不够 | 每块都要停顿 |

程序会在超预算时打印警告，并给出建议的 `--replan-every` 数值，直接照着调即可。

另 `--replan-every` 之外还有一段固定停顿：**采图**。日志里 `块间停顿=` 是
「采图 + 等结果」的合计。实测三路取图约 0–50 ms（相机出的是预编码 JPEG，
直接转发不重编码）；如果看到上百毫秒，多半是 `--fresh-timeout` 在等新帧，
而相机根本没新帧 —— 看同一条日志里的 `帧龄=`。

## 安全边界

客户端会在以下情况直接抛异常退出，不做自动恢复：

- 运控 `error_code != 0`
- 任意关节 `error_code != 0`
- 关节或夹爪反馈缺失、含 NaN/Inf
- 相机拿不到图
- 相机画面停滞超过 `--max-frame-age`（默认 1 s）
- 动作形状不是 `(50,16)`
- 动作块内速度超过 `--max-speed`，或跨块接缝超过 `--max-jump`
- 对齐后剩余步数不够 `--replan-every`

服务器返回 `{"type":"error"}` 时同样退出，不会用上一轮的旧动作继续执行。

## 网络

上行是三路 JPEG 原图（头 400×640，腕部各 1056×1280），约 300–600 KB/帧。
服务器端没有再压缩，保持和训练时的解码路径一致。

带宽不够时可以在机器人侧把腕部相机换成更低分辨率，但**会改变模型输入分布**，
需要重新验证，不要凭感觉调。

局域网直连最理想；走公网建议开 SSH 隧道：

```bash
ssh -N -L 8765:127.0.0.1:8765 root@<服务器> -p <端口>
./run_client.sh --host 127.0.0.1
```
